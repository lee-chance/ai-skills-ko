# 주문 아키텍처 결정의 맥락

주문 서비스는 현재 바꿀 수 있는 주문 행을 저장하고, best-effort
웹훅을 보냅니다. 감사 담당자에게는 상태 전이의 완전한 이력이 필요하고, 지원팀은
과거 한 시점의 주문을 다시 구성할 수 있어야 합니다.

논의한 선택지:

1. 현재 모델을 유지하고 추가 전용 감사 테이블을 더합니다.
2. 주문에 이벤트 소싱을 도입하고 읽기 프로젝션을 만듭니다.
3. 데이터베이스 변경 데이터 캡처를 감사 이력으로 씁니다.

이벤트 소싱은 추적 가능성과 재생을 개선하지만, 프로젝션 재구축,
이벤트 버전 관리, 결과적 일관성, 운영 복잡도를 더합니다. 팀에는
이벤트 스트림 경험이 있지만, 리포팅 서비스는 동기식 읽기를 기대합니다. 이 결정은 주문 바운디드 컨텍스트에만 적용됩니다.
