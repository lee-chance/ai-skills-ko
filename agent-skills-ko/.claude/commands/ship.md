`/ship`은 **팬아웃 오케스트레이터**입니다. 현재 변경에 대해 전문가 페르소나 세 명을 병렬로 실행한 뒤, 그 보고서를 하나의 출시 여부(go/no-go) 결정과 롤백 계획으로 합칩니다. 페르소나는 독립적으로 동작합니다. 공유 상태도 없고 순서도 없습니다. 그래서 여기서 병렬 실행이 안전하고 유용합니다.

## 단계 A. 병렬 팬아웃

Agent 도구로 서브에이전트 세 개를 동시에 생성하세요. **세 번의 Agent 도구 호출을 어시스턴트 턴 하나에 모두 내보내 병렬로 실행되게 하세요.** 순차 호출은 이 명령의 취지를 무너뜨립니다.

Claude Code에서는 각 호출이 페르소나의 `name` 필드와 같은 `subagent_type`을 넘깁니다.

1. **`code-reviewer`**: 스테이징된 변경 또는 최근 커밋에 다섯 축 리뷰(정확성, 가독성, 아키텍처, 보안, 성능)를 실행하세요. 표준 리뷰 템플릿을 출력하세요.
2. **`security-auditor`**: 취약점과 위협 모델 검토를 실행하세요. OWASP Top 10, 시크릿 처리, 인증/인가, 의존성 CVE를 확인하세요. 표준 감사 보고서를 출력하세요.
3. **`test-engineer`**: 변경의 테스트 커버리지를 분석하세요. 정상 경로, 엣지 케이스, 오류 경로, 동시성 시나리오의 빈틈을 찾으세요. 표준 커버리지 분석을 출력하세요.

Agent 도구가 없는 다른 하네스에서는 각 페르소나의 시스템 프롬프트를 순서대로 호출하고, 출력이 병렬로 돌아온 것처럼 다루세요. 병합 단계는 그대로 동작합니다.

제약 (Claude Code의 서브에이전트 모델):
- 서브에이전트는 다른 서브에이전트를 생성할 수 없습니다. 한 페르소나가 다른 페르소나에 위임하게 두지 마세요.
- 각 서브에이전트는 자신의 컨텍스트 창을 갖고, 이 메인 세션에는 보고서만 반환합니다.
- 보고만 하는 것이 아니라 서로 대화하는 팀원이 필요하면 Claude Code Agent Teams를 쓰고, 이 페르소나를 팀원 유형으로 참조하세요 (`references/orchestration-patterns.md` 참조).

**페르소나 해석.** `.claude/agents/` 또는 `~/.claude/agents/`에 직접 정의한 `code-reviewer`, `security-auditor`, `test-engineer`가 있으면, 그 정의가 이 플러그인 버전보다 우선합니다. `/ship`은 그 사용자 정의를 자동으로 사용합니다. 이것은 의도된 동작입니다. 플러그인 서브에이전트는 Claude Code의 범위 우선순위 표 맨 아래에 있으므로, 사용자 수준 정의가 설계상 우선합니다.

## 단계 B. 메인 컨텍스트에서 병합

세 보고서가 모두 돌아오면, 메인 에이전트(하위 페르소나가 아님)가 종합합니다.

1. **코드 품질**: `code-reviewer`의 Critical/Required 발견과, 실패한 테스트, 린트, 빌드 출력을 모으세요. 리뷰어 사이의 중복을 해소하세요.
2. **보안**: `security-auditor`의 Critical/High 발견은 출시 차단 항목으로 올리세요. `code-reviewer`의 보안 축과 대조하세요.
3. **성능**: `code-reviewer`의 성능 축에서 가져오세요. 해당하면 Core Web Vitals를 교차 확인하세요.
4. **접근성**: 키보드 탐색, 스크린 리더 지원, 대비를 확인하세요. 세 페르소나는 이것을 다루지 않습니다. 여기서 직접 처리하거나 접근성 체크리스트를 호출하세요.
5. **인프라**: 환경 변수, 마이그레이션, 모니터링, 피처 플래그입니다. 직접 확인하세요.
6. **문서**: README, ADR, 변경 이력입니다. 직접 확인하세요.

## 단계 C. 결정과 롤백

하나의 출력을 만드세요.

```markdown
## 출시 결정: GO | NO-GO

### 차단 항목 (출시 전에 반드시 수정)
- [출처 페르소나: Critical 발견 + file:line]

### 권장 수정 (출시 전에 고치는 것이 좋음)
- [출처 페르소나: 중요한 발견 + file:line]

### 인지한 위험 (위험을 알고 출시)
- [위험 + 완화]

### 롤백 계획
- 트리거 조건: [어떤 신호가 롤백을 부르는지]
- 롤백 절차: [정확한 단계]
- 복구 목표 시간: [목표]

### 전문가 보고서 (전문)
- [code-reviewer 보고서]
- [security-auditor 보고서]
- [test-engineer 보고서]
```

## 규칙

1. 단계 A의 세 페르소나는 병렬로 실행합니다. 순차로는 실행하지 마세요.
2. 페르소나는 서로를 호출하지 않습니다. 메인 에이전트가 단계 B에서 병합합니다.
3. GO 결정 전에는 롤백 계획이 필수입니다.
4. 어느 페르소나든 Critical 발견을 반환하면, 사용자가 위험을 명시적으로 수용하지 않는 한 기본 판정은 NO-GO입니다.
5. **다음이 모두 참일 때만 팬아웃을 건너뛰세요.** 변경이 파일 2개 이하이고, diff가 50줄 미만이며, 인증, 결제, 데이터 접근, 설정/환경을 건드리지 않습니다. 그렇지 않으면 기본은 팬아웃입니다. `/ship`은 프로덕션으로 가는 변경을 위한 명령입니다. 영향 범위가 사소하지 않으면, diff가 작아 보여도 병렬 리뷰를 실행하세요.
