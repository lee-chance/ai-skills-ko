# 오케스트레이션 패턴

이 저장소가 인정하는 에이전트 오케스트레이션 패턴과, 피할 안티 패턴의 참조 카탈로그입니다. 여러 페르소나를 조율하는 새 슬래시 커맨드를 추가하기 전에, 또는 기존 페르소나를 "감싸는" 새 페르소나를 들이기 전에 읽으세요.

기본 규칙: **사용자(또는 슬래시 커맨드)가 오케스트레이터입니다. 페르소나는 다른 페르소나를 호출하지 않습니다.** 스킬은 페르소나 워크플로우 안의 필수 경유지입니다.

---

## 승인된 패턴

### 1. 직접 호출 (오케스트레이션 없음)

페르소나 하나, 관점 하나, 아티팩트 하나. 기본값이자 가장 싼 선택입니다.

```
user → code-reviewer → report → user
```

**쓸 때:** 작업이 하나의 아티팩트에 대한 하나의 관점이고, 한 문장으로 설명할 수 있을 때.

**예시:**
- "Review this PR" (이 풀 리퀘스트를 리뷰해 줘) → `code-reviewer`
- "Find security issues in `auth.ts`" (`auth.ts`의 보안 문제를 찾아 줘) → `security-auditor`
- "What tests are missing for the checkout flow?" (체크아웃 흐름에 빠진 테스트는 무엇인가?) → `test-engineer`

**비용:** 왕복 한 번. 오케스트레이션된 패턴과 항상 비교해야 하는 기준선입니다.

---

### 2. 단일 페르소나 슬래시 커맨드

프로젝트의 스킬로 페르소나 하나를 감싸는 슬래시 커맨드입니다. 사용자가 매번 워크플로우를 다시 설명하지 않아도 됩니다.

```
/review → code-reviewer (with code-review-and-quality skill) → report
```

**쓸 때:** 같은 단일 페르소나 호출이 같은 설정으로 반복될 때.

**이 저장소의 예시:** `/review`, `/test`, `/code-simplify`.

**비용:** 직접 호출과 같습니다. 슬래시 커맨드는 저장된 프롬프트일 뿐입니다.

**반대 신호:** 슬래시 커맨드 본문이 대부분 "어느 페르소나를 호출할지 결정"이라면 지우세요. 사용자가 페르소나를 직접 호출하게 하세요.

---

### 3. 병합이 있는 병렬 팬아웃

여러 페르소나가 같은 입력을 동시에 다루고, 각자 독립 보고서를 냅니다. 병합 단계(메인 에이전트의 컨텍스트 안)가 그것들을 하나의 결정으로 합성합니다.

```
                    ┌─→ code-reviewer    ─┐
/ship → fan out  ───┼─→ security-auditor ─┤→ merge → go/no-go + rollback
                    └─→ test-engineer    ─┘
```

**쓸 때:**
- 하위 작업이 정말로 독립적일 때 (공유되는 변경 가능 상태가 없고, 순서 의존이 없을 때)
- 각 서브에이전트가 자기 컨텍스트 창에서 이득을 볼 때
- 병합 단계가 메인 컨텍스트에 남을 만큼 작을 때
- 실제 경과 시간(wall-clock)이 중요할 때

**이 저장소의 예시:** `/ship`.

**비용:** 병렬 서브에이전트 컨텍스트 N개와 병합 턴 하나입니다. 직접 호출보다 높지만, 실제 경과 시간은 더 빠르고, 각 서브에이전트가 하나의 관점에 집중하므로 보고서가 더 좋습니다.

**이 패턴을 채택하기 전 검증 체크리스트:**
- [ ] 순서 문제 없이 모든 서브에이전트를 동시에 실행할 수 있습니까?
- [ ] 각 페르소나가 다른 각도에서 같은 발견을 내는 것이 아니라, 다른 *종류*의 발견을 냅니까?
- [ ] 병합 단계가 메인 에이전트에 남은 컨텍스트에 들어갑니까?
- [ ] 사용자의 대기 시간이, 병렬화가 실제로 체감될 만큼 깁니까?

답이 하나라도 "아니요"이면 직접 호출이나 단일 페르소나 커맨드로 돌아가세요.

---

### 4. 사용자가 이끄는 슬래시 커맨드의 순차 파이프라인

사용자가 정해진 순서로 슬래시 커맨드를 실행하고, 그 사이에 컨텍스트(또는 커밋 이력)를 옮깁니다. 오케스트레이터 에이전트는 없습니다. 사용자가 오케스트레이터입니다.

```
user runs:  /spec  →  /plan  →  /build  →  /test  →  /review  →  /ship
```

**쓸 때:** 워크플로우에 의존성이 있고(각 단계가 이전 단계의 출력을 필요로 하고) 단계 사이의 사람 판단이 가치를 더할 때.

**이 저장소의 예시:** 정의(DEFINE) → 계획(PLAN) → 빌드(BUILD) → 검증(VERIFY) → 리뷰(REVIEW) → 출시(SHIP) 수명 주기 전체.

**비용:** 단계마다 서브에이전트 컨텍스트 하나입니다. 오케스트레이터 에이전트가 없으므로 오케스트레이션 계층은 공짜입니다.

**자동화하지 않는 이유:** LLM "수명 주기 오케스트레이터"는 (a) 인계를 위해 요약해야 하므로 단계 사이의 뉘앙스를 잃고, (b) 잘못된 방향의 작업을 일찍 잡는 사람 체크포인트를 건너뛰며, (c) 바꿔 말하는 턴으로 토큰 비용을 두 배로 만듭니다.

---

### 5. 조사 격리 (컨텍스트 보존)

작업이 메인 컨텍스트를 오염시키면 안 되는 많은 자료를 읽어야 할 때, 요약만 돌려주는 조사 서브에이전트를 띄우세요.

```
main agent → research sub-agent (reads 50 files) → digest → main agent continues
```

**쓸 때:**
- 메인 세션이 뒤이은 작업에 집중해야 할 때
- 조사 결과가 소비하는 입력보다 훨씬 작을 때
- 메인 에이전트가 그 뒤에 생각할 여지가 있으면 결정 품질이 좋아질 때

**예시:** "Find every call site of this deprecated API across the monorepo" (이 지원 종료된 API의 호출 지점을 모노레포 전체에서 찾아 줘), "Summarize what these 30 ADRs say about caching." (이 ADR 30개가 캐싱에 대해 말하는 것을 요약해 줘).

**비용:** 격리된 서브에이전트 컨텍스트 하나입니다. 대안이 메인 컨텍스트에 수백 개 파일을 넣는 것이라면 언제든 가치가 있습니다.

**Claude Code에서는 커스텀 조사 페르소나를 정의하지 말고, 내장 `Explore` 서브에이전트를 사용하세요.** `Explore`는 Haiku에서 돌고, 쓰기/편집 도구가 거부되며, 이 패턴을 위해 만들어졌습니다. `Explore`가 맞지 않을 때만 커스텀 조사 서브에이전트를 정의하세요 (예: 모델이 스스로 추론하지 못할 도메인 전용 시스템 프롬프트가 필요할 때).

## Claude Code 호환성

이 카탈로그는 하네스에 묶이지 않지만, 대부분의 독자는 Claude Code에서 실행합니다. 각 패턴이 Claude Code의 기본 요소에 어떻게 대응하는지, 그리고 플랫폼이 어디서 우리 규칙을 대신 강제하는지를 정리합니다.

### 페르소나가 있는 곳

플러그인 서브에이전트는 플러그인 루트의 `agents/`에 둡니다. 이 저장소는 플러그인(`.claude-plugin/plugin.json`)이므로, 플러그인이 켜지면 `agents/code-reviewer.md`, `agents/security-auditor.md`, `agents/test-engineer.md`가 자동으로 발견됩니다. 경로 구성은 필요 없습니다.

### 서브에이전트와 Agent Teams

Claude Code에는 병렬 기본 요소가 두 가지 있습니다. 패턴 3(병합이 있는 병렬 팬아웃)은 **서브에이전트**에 대응합니다. 서로 대화하는 팀원이 필요하면 **Agent Teams**를 사용하세요.

| | 서브에이전트 | Agent Teams |
|--|-----------|-------------|
| 조율 | 메인 에이전트가 팬아웃하고, 서브에이전트는 보고만 합니다 | 팀원이 서로 메시지를 보내고, 작업 목록을 공유합니다 |
| 컨텍스트 | 서브에이전트마다 자기 컨텍스트 창 | 팀원마다 자기 컨텍스트 창 |
| 쓸 때 | 보고서를 내는 독립 작업 | 논의가 필요한 협업 |
| 상태 | 안정 | 실험적. `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`이 필요합니다 |
| 비용 | 더 낮음 | 더 높음. 팀원마다 별도의 Claude 인스턴스입니다 |

**이 저장소의 페르소나는 두 모드에서 모두 동작합니다.** 서브에이전트로 생성되면(예: `/ship`) 발견을 메인 세션에 보고합니다. 팀원으로 생성되면(`Spawn a teammate using the security-auditor agent type…`, security-auditor 에이전트 타입으로 팀원을 생성…) 서로의 발견에 직접 이의를 제기할 수 있습니다. 페르소나 정의는 같고, 생성 컨텍스트만 바뀝니다.

한 가지 미묘한 점: 페르소나의 `skills`와 `mcpServers` frontmatter 필드는 서브에이전트로 돌 때 존중되지만, **팀원으로 돌 때는 무시됩니다.** 팀원은 일반 세션과 같이 프로젝트와 사용자 설정에서 스킬과 MCP 서버를 로드합니다. 페르소나가 특정 스킬이나 MCP 서버가 로드되어 있어야 한다면, 두 모드에서 쓸 수 있도록 세션 수준에서 구성하세요.

### 플랫폼이 강제하는 규칙

이 카탈로그의 규칙 두 가지는 관례가 아닙니다. Claude Code가 강제합니다.

- **"Subagents cannot spawn other subagents"** (문서 원문 그대로). 안티 패턴 B(페르소나가 페르소나를 호출)와 안티 패턴 D(깊은 페르소나 트리)는 Claude Code에서 구조적으로 존재할 수 없습니다.
- **"No nested teams"**. 팀원은 자기 팀을 생성할 수 없습니다. 같은 안티 패턴이 팀 수준에서 막힙니다.

즉, 기여자가 실수로 안티 패턴을 만들어도 걱정 없이 이 카탈로그의 패턴을 채택할 수 있습니다. 그냥 로드에 실패합니다.

### 알아 둘 내장 서브에이전트

커스텀 서브에이전트를 정의하기 전에, 이 중 하나가 역할을 덮는지 확인하세요.

| 내장 | 목적 |
|----------|---------|
| `Explore` | 읽기 전용 코드베이스 검색과 분석. 패턴 5(조사 격리)에 사용하세요. |
| `Plan` | 플랜 모드 중의 읽기 전용 조사. |
| `general-purpose` | 탐색과 수정이 모두 필요한 다단계 작업. |

이것들을 다시 정의하지 마세요. 전문 페르소나(code-reviewer, security-auditor, test-engineer)를 그 위에 올리세요.

### 플러그인 에이전트의 frontmatter 제한

플러그인 서브에이전트는 `hooks`, `mcpServers`, `permissionMode` frontmatter 필드를 **지원하지 않습니다.** 조용히 무시됩니다. 미래의 페르소나에 그중 하나가 필요하면, 사용자가 파일을 `.claude/agents/` 또는 `~/.claude/agents/`로 복사해야 합니다.

플러그인 에이전트에서 동작하는 필드는 다음과 같습니다. `name`, `description`, `tools`, `disallowedTools`, `model`, `maxTurns`, `skills`, `memory`, `background`, `effort`, `isolation`, `color`, `initialPrompt`. 비용을 최적화하려면 페르소나마다 `model`을 사용하세요 (예: `test-engineer` 커버리지 스캔은 Haiku, `code-reviewer`는 Sonnet, `security-auditor`는 Opus).

### 여러 서브에이전트를 병렬로 생성

Claude Code에서 병렬 팬아웃(패턴 3)은 **한 어시스턴트 턴 안에서 Agent 도구 호출을 여러 번** 내야 합니다. 순차 턴은 실행을 직렬화합니다. `/ship`이 이것을 명시합니다. 새 오케스트레이터 커맨드도 같게 해야 합니다.

## 따라 하는 예시: 경쟁 가설 디버깅을 위한 Agent Teams

이 예시는 `/ship`의 서브에이전트 팬아웃 대신 **Agent Teams**를 쓸 때를 보여 줍니다. 두 패턴은 멀리서 보면 비슷합니다. 둘 다 같은 페르소나 셋을 띄웁니다. 가치는 다른 곳에서 옵니다.

### 시나리오

> *체크아웃이 가끔 완료 전에 약 30초 멈춥니다. 대략 세션 50번에 한 번입니다. 로그에 오류가 없습니다. 지난주 릴리스 이후 시작되었습니다.*

그럴듯한 근본 원인 (서로 배타적이고, 모두 증상에 맞습니다):

1. 새 결제 확인 흐름의 경합 조건
2. 가끔 느린 동기 네트워크 호출로 빠지는 인증 확인
3. 장바구니 크기에 따라 늘어나는 쿼리에 인덱스가 없음
4. SDK가 타임아웃 전에 조용히 재시도하는 불안정한 서드파티 API

에이전트 하나는 첫 번째 그럴듯한 이론을 고르고 조사를 멈춥니다. `/ship` 스타일의 서브에이전트 팬아웃은 각 페르소나가 독립적으로 보고하지만, 보고서가 만나지 않으므로 틀린 이론을 배제하는 것이 없습니다.

이것이 바로 Agent Teams 문서가 설명하는 경우입니다. *"여러 독립 조사자가 서로를 적극적으로 반증하려 하면, 살아남는 이론이 실제 근본 원인일 가능성이 훨씬 큽니다."*

### 이것이 `/ship` 작업이 *아닌* 이유

| | `/ship` (서브에이전트) | Agent Teams |
|--|--------------------|-------------|
| 서브에이전트가 보는 것 | 같은 diff, 다른 렌즈 | 공유 작업 목록, 서로의 메시지 |
| 출력 | 독립 보고서 셋, 그다음 병합 하나 | 적대적 토론, 그다음 합의된 근본 원인 |
| 맞을 때 | 알려진 아티팩트에 대한 판정을 원할 때 | 가설 사이에서 아티팩트를 *찾고* 싶을 때 |

`/ship`은 판정입니다. Agent Teams는 조사입니다.

### 설정 (환경마다 한 번)

Agent Teams는 실험적입니다. `~/.claude/settings.json`에서:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

Claude Code v2.1.32 이상이 필요합니다. 이 저장소의 페르소나는 자동으로 잡힙니다. 손으로 작성할 팀 설정 파일은 없습니다.

### 트리거 프롬프트

리드 세션에 자연어로 입력하세요.

```
Users report checkout hangs for ~30 seconds intermittently after last
week's release. No errors in logs.

Create an agent team to debug this with competing hypotheses. Spawn
three teammates using the existing agent types:

  - code-reviewer  — investigate race conditions and blocking calls
                     in the checkout code path
  - security-auditor — investigate auth checks, session handling,
                       and any synchronous network calls added recently
  - test-engineer  — propose tests that would distinguish between the
                     hypotheses and check coverage gaps in checkout

Have them message each other directly to challenge each other's
theories. Update findings as consensus emerges. Only converge when
two teammates agree they can disprove the others'.
```

리드는 기존 페르소나 이름을 참조해 팀원 셋을 생성합니다. 페르소나 본문은 각 팀원의 시스템 프롬프트에 추가 지침으로 **덧붙습니다** (리드가 설치하는 팀 조율 지침 위에). 위의 트리거 프롬프트가 그들의 작업이 됩니다.

### 일어나는 일

1. 각 팀원은 자기 컨텍스트 창에서, 자기 렌즈로 코드베이스를 탐색합니다.
2. 팀원은 `message`로 발견을 서로 직접 보냅니다. 리드가 중계할 필요가 없습니다.
3. 공유 작업 목록은 누가 무엇을 조사하는지 보여 줍니다. 프로세스 내 모드에서는 `Ctrl+T`, 분할 모드에서는 tmux 창에서 언제든 볼 수 있습니다.
4. `code-reviewer`가 순차여야 할 `Promise.all`을 찾으면, 인증 호출이 경합의 일부가 아닌지 확인하라고 `security-auditor`에 메시지를 보냅니다. `security-auditor`가 확인하고 답합니다. 경합이 실제 문제임을 확인하거나, 반증을 냅니다.
5. `test-engineer`는 이기고 있는 이론에 맞춘 통합 테스트를 제안하고, 팀은 합의를 선언하기 전에 그것으로 검증합니다.
6. 리드가 수렴한 발견을 종합해 여러분에게 제시합니다.

`Shift+Down`으로 팀원을 돌며 입력하면 언제든 끼어들 수 있습니다. 잘못된 길로 간 조사자를 되돌릴 때 유용합니다.

### 정리할 때

조사가 근본 원인에 닿으면 리드에게 말하세요.

```
Clean up the team
```

항상 팀원이 아니라 리드를 통해 정리하세요 (문서 기준: 팀원은 정리에 필요한 팀 컨텍스트 전체가 없습니다).

### 비용 기대

조사에 약 10–15분 동안 도는 Sonnet 팀원 셋은, `/ship`이 서브에이전트로 띄운 같은 페르소나 셋보다 눈에 띄게 더 비쌉니다. 이유는 *결론의 품질*입니다. 잘못된 수정이 비싼 프로덕션 디버깅에서는 추가 토큰이 싼 값입니다. 일상적인 풀 리퀘스트 리뷰는 `/ship`을 유지하세요.

### 이 시나리오의 안티 패턴

이것을 서브에이전트를 팬아웃하는 `/debug` 슬래시 커맨드로 **다시 만들지 마세요.** 서브에이전트는 서로 메시지를 보낼 수 없습니다. 패턴을 성립시키는 적대적 토론을 잃게 됩니다. 같은 워크플로우가 계속 나오면, 서브에이전트를 잘못 쓰는 슬래시 커맨드로 감싸지 말고 위의 트리거 프롬프트를 스니펫으로 문서화하세요.

### Agent Teams를 *쓰지 않을* 때

- 알려진 diff에 대한, 프로덕션으로 가는 판정: `/ship`(서브에이전트)을 사용하세요.
- 하나의 아티팩트에 대한 전문가 관점 하나: 페르소나를 직접 호출하세요.
- 순차 수명 주기(스펙 → 계획 → 빌드): 사용자가 이끄는 슬래시 커맨드(패턴 4).
- 작은 요약이 나오는 읽기 위주 조사: 내장 `Explore` 서브에이전트.

팀원이 옳은 답을 내기 위해 서로에게 **이의를 제기해야** 할 때만 Agent Teams를 쓰세요.

## 안티 패턴

### A. 라우터 페르소나 ("메타 오케스트레이터")

어느 다른 페르소나를 호출할지 결정하는 것이 일인 페르소나입니다.

```
/work → router-persona → "this needs a review" → code-reviewer → router (paraphrases) → user
```

**실패하는 이유:**
- 도메인 가치가 없는 순수 라우팅 계층입니다
- 바꿔 말하는 홉이 두 개 늘어납니다. 정보 손실과 대략 2배의 토큰 비용이 생깁니다
- 사용자는 이미 리뷰를 원했습니다. `/review`를 직접 호출할 수 있었습니다
- `AGENTS.md`의 슬래시 커맨드와 의도 매핑이 이미 하는 일을 복제합니다

**대신 할 일:** 슬래시 커맨드를 추가하거나 다듬으세요. 의도에서 커맨드로 가는 매핑을 `AGENTS.md`에 문서화하세요.

---

### B. 다른 페르소나를 호출하는 페르소나

인증 코드를 보면 내부적으로 `security-auditor`를 호출하는 `code-reviewer`.

**실패하는 이유:**
- 페르소나는 하나의 관점을 내도록 설계되었습니다. 체인으로 잇으면 그것이 무너집니다
- 호출하는 페르소나가 넘기는 요약은, 호출되는 페르소나에게 필요한 컨텍스트를 잃습니다
- 실패 모드가 곱해집니다 (어느 페르소나의 출력 형식이 이깁니까? 누구의 규칙이 적용됩니까?)
- 사용자에게 비용을 숨깁니다

**대신 할 일:** 호출하는 페르소나가 보고서에서 후속 감사를 *권고*하게 하세요. 사용자나 슬래시 커맨드가 두 번째 패스를 실행합니다.

---

### C. 바꿔 말하는 순차 오케스트레이터

사용자를 대신해 `/spec`, 그다음 `/plan`, 그다음 `/build` 등을 호출하는 에이전트.

**실패하는 이유:**
- 잘못된 방향의 작업을 잡는 사람 체크포인트를 잃습니다
- 인계마다 컨텍스트를 요약합니다. 긴 파이프라인에서 드리프트가 쌓입니다
- 토큰 비용이 두 배가 됩니다. 모든 단계마다 오케스트레이터 턴과 서브에이전트 턴이 있습니다
- 판단이 가장 중요한 지점에서 사용자의 주도권을 빼앗습니다

**대신 할 일:** 사용자를 오케스트레이터로 두세요. 권장 순서를 `README.md`에 문서화하고, 사용자가 호출하게 하세요.

---

### D. 깊은 페르소나 트리

`/ship`이 `code-reviewer`를 호출하는 `quality-coordinator`를 호출하는 `pre-ship-coordinator`를 호출합니다.

**실패하는 이유:**
- 각 계층이 결정 가치 없이 지연 시간과 토큰을 더합니다
- 디버깅이 여러 수준의 조사가 됩니다
- 잎 페르소나가 여러 요약 단계에서 컨텍스트를 잃습니다

**대신 할 일:** 오케스트레이션 깊이를 최대 1로 유지하세요 (슬래시 커맨드 → 페르소나). 병합은 메인 에이전트에서 일어납니다.

## 결정 흐름

새 오케스트레이션 워크플로우를 고려할 때 이 흐름을 따라가세요.

```
Is the work one perspective on one artifact?
├── Yes → Direct invocation. Stop.
└── No  → Will the same composition repeat?
         ├── No  → Direct invocation, ad hoc. Stop.
         └── Yes → Are sub-tasks independent?
                  ├── No  → Sequential slash commands run by user (Pattern 4).
                  └── Yes → Parallel fan-out with merge (Pattern 3).
                           Validate against the checklist above.
                           If any check fails → fall back to single-persona command (Pattern 2).
```
