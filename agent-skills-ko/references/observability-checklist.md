## 온콜 질문 (여기서 시작)

질문이 없는 텔레메트리는 잡음입니다. 무엇을 계측하기 전에 다음을 확인하세요.

- [ ] 온콜 엔지니어가 이 기능에 대해 물을 질문 2–4개를 적어 둡니다
- [ ] 아래의 모든 신호가 그 질문 중 하나에 대응합니다
- [ ] 각 질문이 맞는 신호 유형과 짝을 이룹니다. 메트릭은 무언가가 잘못되었다는 **사실**을, 트레이스는 **어디**인지를, 로그는 **왜**인지를 말합니다

<a id="structured-logging"></a>

## 구조화 로깅

- [ ] 로그는 구조화된 JSON이며, 자유 형식 문자열이 아니라 안정적인 이벤트 이름을 씁니다
- [ ] 모든 로그 줄에 상관관계/요청 ID가 있습니다. 시스템 경계에서 만들거나 받습니다
- [ ] 상관관계 ID를 모든 아웃바운드 호출과 비동기 경계(HTTP 헤더, 큐 메타데이터)로 전파합니다
- [ ] 진입점이 둘 이상인 로그 스트림(스케줄러, 리플레이 엔드포인트, 수동 실행)에는 진입점 필드가 있습니다. 실행이 시작되는 곳에서 설정하고, 상관관계 ID와 함께 전파합니다
- [ ] 로그 수준이 일관됩니다. `error`는 불변 조건이 깨져 누군가 조치할 수 있음, `warn`은 저하되었지만 처리됨, `info`는 중요한 비즈니스 이벤트, `debug`는 프로덕션에서 꺼짐
- [ ] 어떤 로그 줄에도 시크릿, 토큰, 비밀번호, 가리지 않은 PII가 없습니다(`security-and-hardening`의 절대 규칙)
- [ ] 필드는 허용 목록으로 제한합니다. 요청/응답 본문 전체와 인증 헤더는 넣지 않습니다
- [ ] 외부 서비스 호출은 메타데이터만 기록합니다. 엔드포인트, 상태, 지연 시간, 시도 횟수, 정제한 식별자
- [ ] 실제 로그 출력을 표본으로 확인합니다. 구조화 필드이며, `[object Object]`가 아닙니다

<a id="metrics"></a>

## 메트릭

- [ ] 모든 엔드포인트와 모든 외부 의존성에 **RED**를 계측합니다. Rate, Errors, Duration
- [ ] 모든 리소스(큐, 풀, 호스트)에 **USE**를 계측합니다. Utilization, Saturation, Errors
- [ ] 지연 시간은 히스토그램입니다. p50/p95/p99로 질의할 수 있으며, 평균으로 대체하지 않습니다
- [ ] 모든 레이블은 작고 고정된 집합에서 옵니다(라우트 템플릿, 상태 클래스, 제공자 이름)
- [ ] 끝이 없는 레이블 값을 쓰지 않습니다. 사용자 ID, 테넌트 ID, 이메일, 원본 URL, 요청 ID, 오류 메시지 텍스트는 레이블이 아닙니다
- [ ] 상태 코드는 클래스별로 묶습니다(`5xx`. 개별 코드 `503`을 레이블로 쓰지 않습니다)
- [ ] 모든 워커와 큐에 대해 큐 깊이와 처리 소요 시간을 추적합니다

<a id="distributed-tracing"></a>

## 분산 트레이싱

- [ ] 서비스 기동 시, 다른 import보다 먼저 OpenTelemetry(또는 동등한 구현)를 초기화합니다
- [ ] HTTP, gRPC, DB 클라이언트에 자동 계측을 켭니다
- [ ] 모든 아웃바운드 호출에 트레이스 컨텍스트를 전파하고(W3C `traceparent`/`tracestate`), 모든 인바운드 요청에서 꺼냅니다
- [ ] 컨텍스트가 비동기 경계를 넘습니다. 큐 메시지가 트레이스 메타데이터를 담습니다
- [ ] 수동 스팬은 의미 있는 내부 작업 단위에만 두고, 온콜이 필터할 속성을 붙입니다
- [ ] 스팬 속성에 시크릿이나 PII를 넣지 않습니다
- [ ] 헤드 기반 샘플링의 기본 비율을 낮게 둡니다. 테일 샘플링이 가능하면 오류는 100% 유지합니다

<a id="alerting"></a>

## 알림

- [ ] 모든 알림은 증상 기반입니다(오류율, p99 지연 시간, 큐 대기 시간). 원인(CPU, 디스크, 재시작)은 대시보드로 보내고, 호출로는 보내지 않습니다
- [ ] 모든 알림은 조치할 수 있습니다. "무시하세요, 알아서 회복됩니다" 류의 알림은 삭제합니다
- [ ] 모든 알림이 런북으로 연결됩니다. 최소 세 줄입니다. 의미, 먼저 실행할 쿼리, 에스컬레이션 경로
- [ ] 임계값과 지속 시간은 SLO나 과거 데이터로 근거를 댑니다. 추측으로 정하지 않습니다
- [ ] 심각도는 두 가지만 둡니다. **page**(사용자에게 영향, 지금 조치)와 **ticket**(저하, 이번 주에 조치)
- [ ] 새 알림은 한 번씩 테스트로 발송합니다. 올바른 채널에 도착하고 런북 링크가 동작합니다
- [ ] 매일 울리고, 조치 없이 확인만 되는 알림이 없습니다

<a id="dashboards"></a>

## 대시보드

- [ ] 서비스 상태 대시보드가 있습니다. 오류율, 지연 시간 p99, 트래픽, 포화도
- [ ] 의존성 상태 패널이 서비스별 오류율과 지연 시간을 보여 줍니다
- [ ] 대시보드가 이 체크리스트 맨 위의 온콜 질문에 답합니다. 답만 빠진 차트 모음으로 두지 않습니다
- [ ] 기본 시간 범위가 적절합니다(1시간–6시간. 30일은 기본으로 두지 않습니다)

<a id="verify-the-telemetry"></a>

## 텔레메트리 검증

계측도 코드입니다. 틀릴 수 있습니다.

- [ ] 스테이징에서 오류를 일부러 내고, 상관관계 ID로 로그에서 찾았습니다
- [ ] 테스트 트래픽을 보내면, 기대한 레이블과 타당한 값으로 메트릭 시계열이 나타납니다
- [ ] 트레이싱 UI에서 요청 하나를 끝까지 따라가면 끊긴 스팬이 없습니다
- [ ] 일부러 일으킨 장애를 소스를 읽지 않고 텔레메트리만으로 진단했습니다

<a id="pre-launch-gate"></a>

## 출시 전 관문

기능을 프로덕션에 출시하기 전에 다음이 모두 성립합니다.

- [ ] 구조화 로그가 로그 수집기로 흘러갑니다
- [ ] 새 엔드포인트와 의존성마다 RED 메트릭이 대시보드에 보입니다
- [ ] 증상 기반 알림이 하나 이상 있고, 런북이 있으며, 테스트로 발송했습니다
- [ ] 요청이 거치는 모든 서비스에 걸쳐 트레이스할 수 있습니다
- [ ] 온콜이 런북이 어디 있는지 압니다

출시 당일의 모니터링 순서와 롤백 트리거는 `shipping-and-launch` 스킬을 보세요.
