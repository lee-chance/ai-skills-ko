# 도입 가이드: 새 프로젝트와 자리 잡은 코드베이스

agent-skills를 어떻게 롤아웃할지는 코드베이스가 생애의 어디에 있는지에 크게 좌우됩니다. 그린필드 프로젝트는 첫 커밋부터 전체 생애주기를 도입할 수 있습니다. 수년의 역사가 있는 코드베이스에는, 이미 있는 것, 그 관례, 문서화되지 않은 결정, 그리고 눈감고 건드리고 싶지 않은 곳의 테스트 커버리지 부족을 존중하는 점진적 경로가 필요합니다.

이 가이드는 두 경로를 모두 다룹니다. 설치 방법은 [getting-started.md](getting-started.md)와 도구별 설정 가이드를 보세요. 각 스킬이 하는 일은 [README의 스킬 카탈로그](../README.md#all-25-skills)를 보세요.

---

## 어느 경로인가요?

| 신호                     | 그린필드                      | 브라운필드                                   |
| -------------------------- | ------------------------------- | -------------------------------------------- |
| 코드베이스 나이            | 며칠에서 몇 주                   | 몇 달에서 몇 년                              |
| 테스트 커버리지              | 첫날부터 직접 통제     | 고르지 않음. 테스트가 없는 영역도 있음                  |
| 관례                | 진행하면서 정의               | 이미 자리 잡음. 문서화되지 않은 경우가 많음              |
| 팀 습관                | 형성되는 중                         | 굳어 있음 (좋게든 나쁘게든)             |
| 잘못된 에이전트 변경의 위험 | 영향 범위가 작음                | 고치는 법을 아무도 기억하지 못하는 것을 깨뜨릴 수 있음 |
| 도입 전략          | **즉시 전체 생애주기** | **점진적, 검증 우선**          |

그 사이라면(이미 프로덕션에 출시한 젊은 프로젝트), 브라운필드 경로로 시작한 뒤 속도를 올리세요. 같은 최종 상태로 모입니다.

---

## 경로 A | 그린필드: 첫날부터 전체 생애주기

새 프로젝트는 최선의 경우입니다. 보존할 레거시 동작이 없으므로, 스킬의 품질 게이트는 비용이 거의 없고 첫 커밋부터 복리로 쌓입니다.

### 0일 차 | 설치하고 연결

1. 팩을 설치하세요(`npx skills add addyosmani/agent-skills`, 또는 사용 중인 도구의 네이티브 통합. [getting-started.md](getting-started.md)를 보세요).
2. 호스트에 네이티브 스킬 라우터가 없으면 `using-agent-skills`(메타 스킬)를 로드해서, 에이전트가 스스로 작업을 맞는 스킬로 라우팅하게 하세요. 네이티브 라우팅이 있는 호스트에서는 개별 스킬을 설치하고, 메타 스킬을 항상 켜진 컨텍스트로 미리 로드하지 마세요.
3. 스택, 명령, 경계를 적은 짧은 프로젝트 규칙 파일(`CLAUDE.md`, `.cursorrules` 등)을 추가하세요. 거기에 무엇이 들어가는지는 `context-engineering`이 설명합니다.

### 0일 차 | 만들기 전에 정의

프로젝트의 첫 실제 기능에 대해 생애주기를 순서대로 실행하세요.

```
/spec   →  SPEC.md            (spec-driven-development)
/plan   →  tasks/plan.md      (planning-and-task-breakdown)
/build  →  one slice at a time (incremental-implementation + test-driven-development)
/review →  before every merge  (code-review-and-quality)
/ship   →  when going live     (shipping-and-launch)
```

`/build auto`는 그린필드에 잘 맞습니다. 계획을 한 번 승인하면, 모든 작업은 여전히 테스트 주도이고 개별적으로 커밋됩니다. 스펙과 계획 아티팩트(`SPEC.md`, `tasks/`)는 살아 있는 문서입니다. 작업이 진행되는 동안 버전 관리에 두세요. 기능이 한 세션을 넘으면 그 파일이 핸드오프이기도 합니다. [세션을 넘나들며 작업하기](getting-started.md#working-across-sessions)를 보세요.

### 처음부터 상시로 둘 것

- **test-driven-development**. 커버리지 부채는 0일 때 피하는 비용이 가장 낮습니다.
- **git-workflow-and-versioning**. 원자적 커밋과 약 100줄 변경은 습관이지, 나중에 덧붙이는 것이 아닙니다.
- **security-and-hardening**. 인증, 입력 검증, 시크릿 처리는 구조적입니다. 나중에 덧붙이는 일은 마이그레이션 프로젝트가 됩니다.
- **documentation-and-adrs**. 첫 아키텍처 결정은, 2년 뒤 아무도 *왜*를 기억하지 못할 바로 그 결정입니다. 지금 쓰는 ADR은 경로 B에서 설명하는 브라운필드 고고학을 막아 줍니다.

### 프로젝트가 커지면 추가

| 시점                                | 로드                                                          |
| ----------------------------------- | ------------------------------------------------------------- |
| 첫 공개 API 또는 모듈 경계 | `api-and-interface-design`                                    |
| 첫 UI 작업                       | `frontend-ui-engineering` (+ `browser-testing-with-devtools`) |
| 첫 CI 파이프라인                   | `ci-cd-and-automation`                                        |
| 첫 프로덕션 배포             | `observability-and-instrumentation`, `shipping-and-launch`    |
| 성능 요구사항이 나타날 때     | `performance-optimization`                                    |

### 그린필드 안티패턴

- **"it's just a prototype."(그냥 프로토타입일 뿐)라며 `/spec`을 건너뛰기.** 프로토타입은 제품이 됩니다. 스펙은 이 코드베이스를 위해 쓰게 될 아티팩트 중 비용이 가장 낮습니다.
- **매 세션에 25개 스킬을 모두 로드하기.** 컨텍스트를 낭비하고, 중요한 스킬을 희석합니다. 단계별로 로드하세요. 라우팅은 호스트의 네이티브 라우터 또는 `using-agent-skills` 중 하나만 하게 하고, 둘 다 쓰지는 마세요.
- **옵저버빌리티를 "there's something to observe"(관찰할 것이 있다)가 될 때까지 미루기.** 만들면서 계측하세요. 구조화 로깅을 나중에 끼워 넣는 일은, 스스로 만드는 경로 B 문제입니다.

## 경로 B | 브라운필드: 점진적, 검증 우선

자리 잡은 코드베이스에서는 위험 프로필이 뒤집힙니다. 위험은 잘못된 것을 만드는 일이 아니라, 동작을 아무도 완전히 스펙하지 않은 것을 *바꾸는* 일입니다. 그래서 도입 순서는 코드베이스를 **읽고 보호하는** 스킬에서 시작하고, 그것을 **바꾸는** 스킬로는 나중에 이동합니다.

### 1단계 | 컨텍스트와 읽기 전용 스킬

목표: 에이전트는 무엇을 수정하기 전에 코드베이스를 이해합니다.

1. **`context-engineering`을 먼저.** 코드에 있는 실제 관례를 설명하는 프로젝트 규칙 파일을 작성하세요. 위키에 있는 관례가 아닙니다. 빌드/테스트 명령, 디렉터리의 의미, 알려진 함정을 넣으세요. 예를 들어 "don't touch `legacy/billing`, it has no tests and three known workarounds"라고 적습니다. `legacy/billing`은 테스트가 없고 알려진 우회가 세 가지이니 건드리지 말라는 뜻입니다.
2. **들어오는 변경에 `code-review-and-quality`.** 리뷰는 위험이 없고 바로 가치가 있습니다. 다섯 축 리뷰와 심각도 라벨(머지를 막는 것인 Critical과 Required를, 막지 않는 것과 가릅니다)은 코드베이스 상태와 관계없이 어떤 풀 리퀘스트에서든 동작합니다.
3. **어차피 고치던 버그에는 `debugging-and-error-recovery`.** 다섯 단계 분류(재현 → 국소화 → 축소 → 수정 → 가드)는 낯선 코드에서 잘 맞고, 가드 단계는 아직 없는 회귀 스위트를 쌓기 시작합니다.
4. **안전망으로 `doubt-driven-development`.** 레거시 코드는 이 스킬이 노리는 "낯선 코드, 틀렸을 때의 비용이 큼" 시나리오 그 자체입니다. 레거시 시스템이 어떻게 동작하는지에 대한 에이전트의 주장을, 적대적인 새 컨텍스트에서 리뷰하면 확신에 찬 환각이 커밋이 되기 전에 잡힙니다.

### 2단계 | 변경 전에 테스트

목표: 에이전트가 건드릴 모든 영역에 먼저 안전망을 깝니다.

- **`test-driven-development`를 선택적으로 적용합니다.** 전역 커버리지를 목표로 하지 마세요. *변경이 예정된 곳*의 커버리지를 목표로 하세요. 테스트되지 않은 레거시 동작에는 특성화 테스트를 작성하세요. 수정 전에, 맞든 틀리든 코드가 지금 하는 일을 고정하는 테스트입니다. Beyonce Rule이 적용됩니다. 에이전트가 어떤 동작에 의존할 만큼 그것을 좋아했다면, 그 동작에 테스트를 달아 두었어야 합니다.
- **가장 심한 핫스팟에는 `code-simplification`.** 작동 원리는 Chesterton's Fence입니다. 이 스킬은 에이전트가 코드를 제거하기 전에 그 코드가 *왜* 존재하는지 이해하도록 강제합니다. 동작을 보존하는 단순화에 특성화 테스트를 더하는 것이, 레거시 코드를 변경 가능하게 만드는 가장 위험이 낮은 방법입니다.
- **`git-workflow-and-versioning`을 어디에나.** 작고 원자적인 커밋은 브라운필드에서 *더* 중요합니다. 오래된 코드를 바꾼 변경이 미묘한 것을 깨뜨릴 때, 약 100줄 커밋은 `git bisect`로 좁힐 수 있고, 2,000줄짜리 "현대화" 커밋은 그렇지 않습니다.

### 3단계 | 새 작업은 전체 생애주기

목표: 이중 속도 도입입니다. 레거시 코드는 1–2단계 체제를 유지하고, **새 기능은 그린필드와 같이 다룹니다**.

- 오래된 코드베이스의 새 기능인가요? `/spec → /plan → /build → /review`. 스펙의 경계 섹션에서, 기능이 건드려도 되는 레거시 표면과 건드리면 안 되는 표면을 선언하세요.
- **이음매에서 `api-and-interface-design`.** 새 코드가 오래된 코드와 이야기해야 할 때, 경계를 계약 우선으로 설계하세요. 수년 된 코드베이스에서 Hyrum's Law는 이론이 아닙니다. 누군가는 버그를 포함해 관찰 가능한 모든 동작에 의존합니다.
- **`security-and-hardening`은 감사로, 그다음 게이트로.** 기존 공격 표면(인증, 입력 처리, 의존성. 의존성 감사만으로도 보통 이 작업의 값은 합니다) 전체에 한 번 실행하고, 발견한 내용을 기록한 다음, 새 변경에는 게이트로 적용하세요.

### 4단계 | 갚고, 지원 종료하고, 관찰

- **`deprecation-and-migration`**은 브라운필드 스킬의 전형입니다. 부채로서의 코드, 강제 지원 종료와 권고 지원 종료, 좀비 코드 제거는 레거시 표면을 감싸기만 하는 대신 줄이는 규율 있는 방법을 줍니다.
- **`observability-and-instrumentation`**은 실제로 디버깅하는 경로를 따라 나중에 끼워 넣습니다. 구조화 로깅과 RED 메트릭은 인시던트가 가장 많은 출처부터 두세요.
- **`performance-optimization`**은 회귀가 문제일 때입니다. 측정 우선 규칙은, 병목이 아니었던 코드를 최적화하는 전형적인 레거시 함정을 막습니다.

### 브라운필드 안티패턴

- **"빅뱅" 도입.** 첫날에 레거시 코드베이스에 전체 생애주기를 올리면, 이미 있는 코드에 대한 스펙과 안전망 없는 리팩터가 나옵니다. 순서를 지키세요.
- **테스트되지 않은 코드를 에이전트가 리팩터하게 두기.** 특성화 테스트가 없으면 리팩터도 없습니다. 브라운필드 도입에서 가장 비싼 지름길입니다.
- **`context-engineering`을 "코드가 문서니까"라고 건너뛰기.** 에이전트는 우연히 읽은 최악의 파일에서 관례를 추론합니다. 실제 관례를 알려 주세요.
- **레거시 시스템의 동작을 기본적으로 틀렸다고 다루기.** Chesterton's Fence입니다. 이상한 재시도 루프가 전체를 떠받치고 있을 수 있습니다. 이해한 다음 바꾸세요.
- **아무것도 고정하지 않기.** 도입은 품질이 한 방향으로만 더 나아지게 해야 합니다. 각 단계는 다시 풀리지 않는 게이트를 더합니다. 한 달이 지나도, 이전에는 강제되지 않던 것 중 지금 강제되는 것을 댈 수 없다면 롤아웃은 멈춘 것입니다.

---

## 두 경로는 같은 곳으로 모입니다

둘 다 같은 안정 상태로 끝납니다. 새 작업에는 `/spec → /plan → /build → /review → /ship`, 상시 TDD와 git 규율, 머지 전 리뷰 게이트, 그리고 한꺼번에가 아니라 단계별로 로드하는 스킬입니다. 그린필드는 며칠이면 도달하고, 브라운필드는 한 분기면 도달합니다. 차이는 정확히, 오래된 코드베이스에 원래 없던 안전망(컨텍스트, 특성화 테스트, 경계)입니다.

|                        | 그린필드                     | 브라운필드                               |
| ---------------------- | ------------------------------ | ---------------------------------------- |
| 처음 로드하는 스킬     | 네이티브 라우터, 또는 `using-agent-skills` + `/spec` | `context-engineering`                    |
| 처음 전달하는 가치  | 스펙이 있고 테스트부터 한 첫 기능   | 위험 없는 리뷰와 더 안전한 버그 수정    |
| TDD 자세            | 첫 커밋부터 전면      | 선택적: 변경이 예정된 곳에 테스트 |
| 리팩터 규칙       | 드묾 (리팩터할 것이 적음)      | 항상 특성화 테스트부터     |
| 가장 위험한 안티패턴  | 스펙 건너뛰기              | 테스트 없는 코드 리팩터                |
| 전체 생애주기까지 | 첫날                        | 약 한 분기, 그 사이는 이중 속도       |
