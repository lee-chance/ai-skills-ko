# agent-skills는 어떻게 다른가

사람들이 자주 묻는 질문이 있습니다. **agent-skills**가 가장 자주 거론되는 다른 두 "코딩 에이전트용 스킬" 모음, 즉 **Superpowers**(Jesse Vincent / obra)와 **Matt Pocock's skills**와 어떤 관계인지입니다. 셋 모두 좋고, DNA를 많이 공유하며, 배울 점이 있습니다. 이 페이지는 세 프로젝트가 *형태*에서 어떻게 다른지를 있는 그대로 보여 줍니다. 일하는 방식에 맞는 것을 고르거나, 셋에서 필요한 것을 빌려 쓸 수 있습니다.

> **핵심:** 세 프로젝트는 서로 다른 순간에 맞춰 최적화되어 있습니다. **agent-skills**는 *제품 수명 주기 전체*(정의, 계획, 빌드, 검증, 리뷰, 출시)를 정리하고, 리뷰 페르소나, 합리화 방지 가드, 스킬이 실제로 라우팅되고 기대한 대로 동작하는지 확인하는 저장소 내 eval 프레임워크를 둡니다. **Superpowers**는 서브에이전트, 엄격한 파이프라인, worktree 격리를 앞세운 *자율적이고 추론 비중이 큰* 실행에 기울어 있습니다. **Matt Pocock's skills**는 한 전문가의 일상 워크플로우를 압축한 *날카롭고 의견이 뚜렷한 Claude Code 도구 모음*이며, 대표적인 "grill me" 질문 루프가 있습니다. 추상적으로 "최고"인 것은 없습니다. 앞에 놓인 작업에 따라 달라집니다.

## 한눈에 보기

| | **agent-skills** | **Superpowers** | **Matt Pocock's skills** |
|---|---|---|---|
| **핵심 아이디어** | 시니어 엔지니어링 수명 주기 전체를 스킬로 부호화합니다 | 조합 가능한 스킬 위에 세운 완전한 개발 *방법론* | 한 전문가의 Claude Code 워크플로우를 오픈소스로 공개하고 계속 발전시킵니다 |
| **구성 원리** | 메타 스킬 라우터 뒤에 둔 SDLC **단계**(정의(Define)에서 출시(Ship)까지) | 하나의 규율 있는 루프: 브레인스토밍, 계획, 실행, 리뷰 | 초점이 분명하고 조합 가능한 명령을 모은 큐레이션된 도구 상자 |
| **카탈로그 규모** | 수명 주기 전체를 아우르는 스킬 25개 | 내부 빌드 루프에 깊이 있는 스킬 약 14개 | 엔지니어링 / 생산성 / in-progress(진행 중) / deprecated(지원 종료)로 묶인 스킬 약 30개 |
| **수명 주기 범위** | 넓음: 아이디어 정제, API와 UI 설계, 보안, 성능, CI/CD, 옵저버빌리티, 지원 종료, ADR, 출시 | 깊지만 좁음: TDD, 디버깅, 계획, 리뷰, 스킬 작성 | 정의(Define)와 빌드(Build) 비중이 큼: grilling, PRD, 이슈, TDD, 아키텍처, 버그 분류, 지식 관리 |
| **진입점** | 단계와 1:1로 대응되는 슬래시 커맨드(`/spec` `/plan` `/build` `/test` `/review` `/code-simplify` `/ship`, 그리고 `/webperf`). `/build auto` 전체 계획 모드 포함 | 스킬이 이어지는 파이프라인(`brainstorming`, `writing-plans`, `subagent-driven-development`) | 슬래시 커맨드(`/grill-me`, `/tdd`, `/to-prd`, `/diagnosing-bugs`, `/grill-with-docs`) |
| **특징적인 장치** | 모든 스킬의 합리화 방지 표와 레드 플래그. `/ship`의 병렬 리뷰 **페르소나**. 참조 체크리스트. CI의 **3티어 eval 프레임워크** | 작업 리뷰어(스펙과 품질)와 수정 루프가 있는 서브에이전트 주도 개발. git worktree 격리. 압박 테스트를 거친, 스킬을 작성하는 스킬 | **grilling** 기본 요소(한 번에 질문 하나, 설계 트리 순회). 심(seam) 기반 TDD. 사용자 호출과 모델 호출의 명시적 분리. 이슈 트래커 연동 |
| **품질 측정** | 카탈로그를 대상으로 트리거, 라우팅, 행동 eval을 실행합니다(저장소 안, 일부는 CI) | 압박 테스트 방법론이 철학의 핵심입니다. eval 스위트 자체는 이제 별도 저장소에 있습니다 | 저장소에 포함된 것은 없습니다 |
| **도구 범위** | Claude Code, Cursor, Gemini CLI, Antigravity, OpenCode, Windsurf, Copilot, Kiro, Codex, Command Code, 그리고 `npx skills` CLI | 가장 넓고 변경이 잦은 지원 범위 중 하나: Claude Code, Codex, Cursor, Copilot CLI, OpenCode, Kimi, Factory Droid, Antigravity, Pi | Claude Code가 우선입니다. `npx skills add`로 배포합니다. 다른 에이전트는 충실도가 제각각입니다 |
| **거버넌스** | 커뮤니티 기여를 적극적으로 리뷰하고 머지합니다. 모든 스킬에 eval이 함께 나갑니다 | 대체로 단독 작성입니다. 머지되지 않은 커뮤니티 풀 리퀘스트가 상당히 쌓여 있습니다 | 단독 작성이고, 스스로 머지하며, 공개된 자리에서 개발합니다 |
| **가장 잘 맞는 경우** | 각 단계마다 사람 체크포인트를 두고 기능을 모든 단계로 이끌 때 | 길고 자율적이며, 추론 비중이 크거나 탐색적인 작업 | 실전에서 검증된 실용적인 일상 루프. 요구사항과 TDD에서 가장 강합니다 |

*(스타 수와 도입 수치는 일부러 빼 둡니다. 블로그마다 인용 수치가 크게 다르고, 매주 바뀝니다. 셋 모두 활발히 쓰이고 유지되고 있습니다.)*

## 세 프로젝트를 각자의 말로

### Superpowers (obra)

조합 가능한 스킬 위에 세운 완전한 소프트웨어 개발 *방법론*입니다. **자율성과 사전 추론**에 베팅합니다. 세션은 의도적으로 선형인 파이프라인을 탑니다. 날짜가 적힌 스펙을 쓰고 핸드오프를 정확히 한 번만 허용하는 소크라테스식 브레인스토밍, "열의는 있지만 안목은 별로고 맥락도 없는 주니어 엔지니어"가 실행할 수 있도록 쓴 상세 계획, 그다음 서브에이전트 주도 실행입니다. 새 서브에이전트가 각 작업을 구현하고, 작업 리뷰어가 스펙 준수와 코드 품질을 모두 승인한 뒤에야 작업이 닫히며, 지적된 것은 수정 루프로 돌아가고, 마지막에는 가장 능력 있는 모델로 브랜치 전체를 리뷰합니다. Git worktree는 병렬 작업을 격리하고, `writing-skills` 스킬은 문서 자체에 TDD를 적용합니다. 실패하는 테스트를 먼저 두지 않으면 어떤 스킬도 나가지 않습니다.

강점은 실재합니다. 꽤 큰 덩어리를 넘기고 돌아오면 이미 리뷰된 결과가 있고, 에이전트가 과정을 합리화해서 건너뛰지 못하게 하는 가드레일이 강합니다. 트레이드오프는 그 규율의 이면입니다. 범위는 좁습니다(보안에서 출시까지의 수명 주기가 아니라, 내부 루프 빌드 방법론입니다). 단일 파이프라인은 작은 변경에서 무겁게 느껴질 수 있고, 최근 방향은 그 비용을 줄이는 쪽입니다. 예를 들어 작업 리뷰어를 하나로 모아, 속도는 대략 두 배, 토큰은 절반으로 만들었습니다. 커뮤니티가 가장 크게 계속 요청하는 멀티 에이전트 팀 실행은 아직 포함되어 있지 않습니다.

**저장소:** <https://github.com/obra/superpowers>

### Matt Pocock's skills

Matt은 자신이 실제로 쓰는 Claude Code 스킬을 오픈소스로 공개했고, 모음은 공개적으로 정리된 넓고 의견이 뚜렷한 도구 상자로 자랐습니다. 스킬이 말하는 규율을 그대로 보여주는 `in-progress/`와 `deprecated/` 디렉터리도 눈에 보이게 둡니다. 무게 중심은 TDD가 아니라 **grilling**입니다. 한 번에 질문 하나를 던지고, 설계 트리의 각 가지를 걸으며 의존성을 순서대로 해소하고, 질문마다 권장 답을 제시하고, 묻기보다 코드베이스를 읽는 쪽을 선호하며, 공유된 이해를 확인할 때까지 진행을 거부하는 재사용 가능한 질문 루프입니다. `grill-me`와 `grill-with-docs`는 그 위의 얇은 래퍼입니다. TDD 스킬도 특색이 있고, 유쾌할 정도로 정통에서 벗어납니다("리팩터는 루프의 일부가 아니다", 그것은 코드 리뷰에 속한다). 에이전트 컨텍스트를 부족한 예산으로 다루려고, 사용자 호출 스킬과 모델 호출 스킬을 의도적으로 나눕니다.

강점은 진정성과 날카로움입니다. 위원회가 구상한 프레임워크가 아니라, 아주 뛰어난 엔지니어 한 명이 실제로 출시하는 방식이고, 요구사항을 grilling하는 루프는 정말로 훌륭합니다. 트레이드오프: 실무에서는 Claude Code가 우선입니다(다른 에이전트에서는 신뢰성의 거친 면이 드러납니다). 회귀를 잡는 저장소 내 eval이 없고, 빌드(Build) 이후의 수명 주기 범위는 얇으며, 일부 스킬은 개인용 설정 마법사와 트래커 관례에 묶여 있습니다. 최근 작업은 단일 세션 스킬에서, 이슈 트래커를 통한 다중 세션 오케스트레이션으로 밀고 있습니다(진행 중인 `wayfinder`).

**저장소:** <https://github.com/mattpocock/skills> · 관련: <https://github.com/mattpocock/agent-rules-books>

### agent-skills (이 프로젝트)

agent-skills는 **제품 수명 주기 전체**를 스킬로 정리하고, 작업을 알맞은 스킬로 라우팅하는 메타 스킬(`using-agent-skills`)을 둡니다. 모든 스킬에는 **흔한 합리화(Common Rationalizations)** 표(에이전트가 단계를 건너뛰려고 드는 변명과, 각각에 대한 반박)와 **레드 플래그**가 있습니다. 슬래시 커맨드는 수명 주기 단계와 일대일로 대응합니다. `/build auto`는 승인된 계획 전체를 한 번에 실행하고, `/ship`은 리뷰 **페르소나**(`code-reviewer`, `security-auditor`, `test-engineer`, `web-performance-auditor`)를 병렬로 펼친 뒤 진행/중단(go/no-go)으로 합칩니다. 각 단계에 사람 체크포인트를 두고, 완료 정의를 포함한 참조 체크리스트 일곱 개를 함께 제공하며, 주요 에이전트 도구 대부분에서 돌아갑니다. 그중 여러 곳은 명령 한 번으로 설치합니다.

더 새롭고 지금의 차별점인 것은, 저장소 안에 있는 **3티어 eval 프레임워크**입니다. 티어 1은 구조를 확인하고, 티어 2는 각 스킬의 `description`이 사용자가 실제로 말하는 어휘를 담는지, 그리고 라우팅에서 두 스킬이 충돌하지 않는지를 확인합니다(결정적이며 CI에서 실행됩니다). 티어 3은 에이전트의 실제 실행 트레이스를 스킬별 기대와 대조해 채점합니다. 다른 둘은 오늘날 이런 종류의 저장소 내, 카탈로그 전체 측정을 포함하지 않습니다. 반대 방향의 정직한 트레이드오프도 있습니다. agent-skills는 Superpowers만큼 단일한, 의견이 뚜렷한 "실행"이 적고, 셋 모두 세션을 넘는 지속적인 메모리를 아직 잘 풀지 못했습니다.

## 실제 정면 비교: Superpowers와 agent-skills

Om Mishra는 통제된 실험을 했습니다. Claude Code에서 같은 모델, 같은 저장소, 같은 프롬프트로, 바꾼 것은 스킬 프레임워크뿐이었고, 그 결과를 글로 남겼습니다.

**["Superpowers vs Agent-Skills: Faster Shipping, Safer Reasoning"](https://www.linkedin.com/pulse/superpowers-vs-agent-skills-faster-shipping-safer-reasoning-om-mishra-dzakf/)** 저자 Om Mishra

공정하게 요약하면:

- **agent-skills**는 코드로 더 빨리 넘어갔습니다(약 8분 대 약 12분). **검증 패스도 더 많이** 돌렸습니다(7 대 5, 전체 테스트 스위트 포함). 그 더 넓은 검증은, 기능 전용 테스트가 놓친, 당면 기능 *바깥*의 호환성 문제를 잡았습니다. 그는 그 작업에서 **검증 깊이**의 우위를 agent-skills에 줬습니다.
- **Superpowers**는 **사전 아키텍처 추론**에 더 투자했고, 그는 진화하는 프로덕션 시스템과, 따를 확립된 패턴이 없는 탐색 작업에서 여전히 이쪽을 매일 쓰는 기본 도구로 선호합니다.
- 토큰 효율은 사실상 같았습니다. 둘 다 한 번씩 다시 계획했습니다.

한 개발자의 단일 작업 실험이며, 벤치마크는 아닙니다. 그래도 핵심 트레이드오프를 구체적으로 보여 줍니다. **넓은 규율 있는 검증과, 무거운 사전 추론**입니다. 그 자신의 결론이 정직한 결론입니다. 작업에 맞춰 도구를 고르세요.

## 무엇을 쓸지 정하는 방법

한눈에 보기 표는 형태를 알려 줍니다. 아래는 실무에서 고르는 방법입니다.

### 작업의 형태에서 시작하세요

- **기능 하나를 앞에서 뒤까지 전부?** agent-skills입니다. 셋 중 스펙에서 보안, 성능, 출시까지, 각 단계의 체크포인트와 함께 데려가는 것은 이것뿐입니다. 그래서 리뷰나 사전 점검이 조용히 빠지지 않습니다.
- **넘긴 뒤 자리를 뜨고 싶은, 크고 모호한 덩어리?** Superpowers입니다. 파이프라인과 서브에이전트 리뷰는 오래 실행되고, 스펙과 대조해 이미 리뷰된 결과를 돌려주도록 만들어져 있습니다.
- **빠르고 초점 있는 일상 루프, 특히 코드 전에 요구사항을 바로잡는 일?** Matt Pocock's skills입니다. grilling 루프는 셋 중 가장 날카로운 요구사항 도구이고, 도구 모음은 일을 방해하지 않습니다.

### 그다음, 실제로 중요한 것에 가중치를 두세요

- **범위의 폭**(보안, 성능, CI/CD, 옵저버빌리티, 출시): agent-skills가 분명한 선택입니다. 나머지는 내부 루프에 초점이 있습니다.
- **긴 실행에서의 자율성**: 설계상 Superpowers입니다.
- **작은 변경에서 절차를 가볍게**: Pocock의 도구 모음이 가장 가볍습니다. agent-skills는 그 중간입니다(작은 변경은 `/test`와 `/review`로 바로 갈 수 있습니다). Superpowers가 절차가 가장 무겁습니다.
- **스킬 자체가 동작한다는 확신**: 저장소에 카탈로그 전체 eval이 있는 것은 agent-skills뿐입니다. 그래서 `description`이나 라우팅 회귀는 CI에서 실패합니다. 나중에 "why didn't the skill fire"(왜 스킬이 발동하지 않았지)라는 알 수 없는 증상으로 나오지 않습니다.
- **요구사항을 캐묻는 일**: Pocock의 grilling이 참조 구현입니다. agent-skills의 `interview-me`는 취지가 가깝고, 선택적인 협업 모드를 더하는 중입니다.
- **플랫폼 범위**: agent-skills와 Superpowers는 거의 어디서나 돌아갑니다. Pocock은 Claude Code에서 가장 잘 맞습니다.
- **각 단계의 사람 관문과, 개입 없이 끝까지 도는 실행**: agent-skills는 기본적으로 체크포인트를 둡니다. Superpowers는 실행 중 확인을 의도적으로 최소화합니다.

### 구체적인 시나리오

- *"인증, 테스트, 보안 점검을 갖춘 새 엔드포인트를 머지 전에 출시한다."* agent-skills: `/spec`에서 `/ship`까지, 마지막에 security-auditor와 test-engineer 페르소나가 펼쳐집니다.
- *"얽힌 서브시스템을 밤새 리팩터하고 아침에 리뷰한다."* Superpowers: 계획을 넘기고, 서브에이전트 주도 개발과 작업 리뷰어가 실행되게 둡니다.
- *"아이디어는 흐릿한데, 에이전트가 요구사항을 추측하게 두고 있다."* 코드를 쓰기 전에 의도를 고정하려면 Pocock의 `grill-me`(또는 agent-skills의 `interview-me`)를 쓰세요.
- *"명확한 버그 하나를 테스트 우선으로 고친다."* 어느 것이든 됩니다. 이미 설치해 둔 것 중 가장 가벼운 것을 쓰세요.
- *"한 저장소에서 엔지니어 팀이 에이전트를 쓰는 방식을 표준화한다."* agent-skills: 단계 명령, 페르소나, 공유 체크리스트가 팀에 공통 어휘를 주고, eval이 커스텀 스킬을 정직하게 유지합니다.
- *"직접 스킬을 만들고, 올바르게 트리거되는지 알고 싶다."* agent-skills를 쓰고, 합리화로 넘어가면 안 되는 스킬에는 Superpowers의 압박 테스트 규율을 빌리세요.

### 혼자와 팀

혼자 개발할 때는 취향과 탄력이 이깁니다. 기본값이 이미 일하는 방식과 맞는 것을 고르세요. 절차가 가장 적은 옵션이 가장 자주 쓰이는 경우가 많습니다. 팀에서는 계산이 공유된 구조와 강제할 수 있는 가드레일 쪽으로 기울어집니다. 이름이 있는 단계, 리뷰 페르소나, 체크리스트, CI를 실패시키는 eval이, 다섯 사람(과 그들의 에이전트)을 다섯 개의 사적인 워크플로우가 아니라 같은 기준으로 모읍니다. agent-skills가 만들어진 상황이 그것입니다. 다만 팀은 그 안에서 Superpowers의 리뷰 규율이나 Pocock의 grilling 루프를 얼마든지 받아들일 수 있습니다.

### 공유된 프론티어(셋 모두 해당)

셋 모두 **세션을 넘는 지속적인 메모리**를 아직 잘 풀지 못했습니다. 한 세션에서 에이전트가 배운 것이 다음 세션으로 깨끗하게 이어지는 일이 드뭅니다. 셋 모두 그 주변을 돌고 있습니다(학습 파일, 핸드오프 아티팩트, 트래커에 기댄 계획 지도). 그것이 병목이면, 오늘 어느 쪽이 제공하는 범위의 가장자리에 있다는 점을 알아 두세요. 당분간은 일부를 직접 이어 붙여야 합니다.

## 함께 쓰기

하나만 배타적으로 고를 필요는 없습니다. 다만 합칠 때는 조심하세요. 이들은 런타임이 아니라 Markdown 스킬이므로, *개별* 스킬을 골라 쓰는 것은 잘 됩니다. Pocock의 `grill-me`, Superpowers의 격리 패턴, 또는 특정 체크리스트를 주 설정 옆에 가져오세요.

잘 되지 않는 것은 둘을 **동시에 활성 라우터**로 돌리는 것입니다. 겹쳐 둔 메타 스킬은 명령 이름을 두고 다투고(`/tdd`가 두 곳에 정의됨), 라우팅 로직에서 경쟁하며, 서로 다른 TDD 철학을 끌어옵니다. 그래서 양쪽의 장점 대신 예측할 수 없는 동작이 나옵니다. 프레임워크 하나를 주 라우터로 고르고, 나머지는 필요한 것만 골라 빌리세요.
