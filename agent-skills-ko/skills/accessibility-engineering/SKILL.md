# Accessibility Engineering

## 개요

접근성은 다듬기 단계가 아닙니다. 많은 지역에서 법적 요구 사항이고, 엔지니어링 품질 기준이며, 출시의 전제 조건입니다. 이 스킬은 기존 인터페이스를 감사하고, 발견 사항을 분류하고, 검증된 위반을 수정합니다. 목표는 자동화 도구와 수동 테스트로 뒷받침되는 WCAG 2.2 AA 준수입니다.

## 사용 시점

- 접근성 감사가 필요한 사용자 대면 변경을 출시하기 전
- a11y 문제가 보고되었을 때 (예: "스크린 리더가 이걸 읽지 못함", "키보드 탐색이 깨짐")
- 기존 인터페이스를 준수 여부로 감사할 때
- axe-core나 pa11y 발견 사항을 분류할 때
- 검증된 접근성 위반을 수정할 때

**사용하지 말아야 할 때**: 새 UI 컴포넌트를 처음부터 만드는 일에는 쓰지 말고, 구성 가이드는 `frontend-ui-engineering`을 사용하세요. 백엔드 전용 변경, CLI, UI 출력이 없는 라이브러리 코드에도 쓰지 마세요.

## 워크플로우

### 1단계: 새 UI 작업 라우팅

컴포넌트 구성, 상호작용 패턴, 포커스 관리 가이드는 `../frontend-ui-engineering/SKILL.md`를 사용하세요. 그 스킬의 내용을 여기에 다시 적지 마세요. 인터페이스가 존재하고 감사나 수정이 필요해지면 이 워크플로우로 돌아오세요.

### 2단계: 자동화 감사 실행

접근성 검사를 다음 순서로 실행하세요.

```bash
# axe-core rules through pinned @axe-core/cli (the axe-core package ships no CLI)
npx --yes @axe-core/cli@4.13.0 http://localhost:3000 --exit

# Keep the JSON for the accessibility-auditor
npx --yes @axe-core/cli@4.13.0 http://localhost:3000 --dir ./a11y-reports --save axe.json

# Pinned pa11y for HTML validation (WCAG2AA rules via HTML_CodeSniffer)
npx --yes pa11y@9.1.1 http://localhost:3000
```

통합 보고서가 필요하면 `bash skills/accessibility-engineering/scripts/audit-a11y.sh url <url> --json`을 실행하세요. 고정된 두 도구를 모두 실행하고, 각 도구의 상태와 버전을 기록하며, 어느 한쪽이 유효한 보고서를 만들지 못하면 깨끗한 결과로 보고하지 않고 실패합니다.

위반을 심각도별로 묶어 검토하세요.
- **Critical**: 스크린 리더 접근을 완전히 막습니다 (정보 이미지의 alt 텍스트 누락, 빈 버튼)
- **Serious**: 콘텐츠에 접근하기 어렵거나 불가능하게 만듭니다 (낮은 대비, 레이블 누락)
- **Moderate**: 혼란이나 추가 노력을 일으킵니다 (제목 수준 건너뜀, 불필요한 ARIA)
- **Minor**: 외관상의 문제이거나 점진적 향상입니다 (내부 요소의 lang 속성 누락)

각 위반은 브라우저에서 해당 요소를 직접 확인해 오탐이 아닌 실제 문제인지 검증하세요.

### 3단계: 수동 테스트

자동화 검사는 연기 테스트(smoke test)이지 준수의 증명이 아닙니다. 감사는 수동으로 마무리하세요.

**키보드 감사:**
1. 상호작용 요소를 모두 Tab으로 이동합니다. 현재 위치가 보입니까?
2. Enter/Space로 버튼과 링크를 활성화합니다
3. Escape로 모달을 닫습니다
4. 화살표 키로 목록을 탐색합니다
5. 키보드 트랩이 없는지 확인합니다

**스크린 리더 감사 (macOS는 VoiceOver, Windows는 NVDA):**
1. 제목으로 탐색합니다 (VoiceOver: Ctrl+Option+Cmd+H). 구조가 논리적입니까?
2. 랜드마크로 탐색합니다 (Ctrl+Option+U로 로터를 열고 Landmarks 선택). 영역에 레이블이 있습니까?
3. 링크로 탐색합니다 (Ctrl+Option+U로 로터를 열고 Links 선택). 링크 설명이 맥락 없이도 이해됩니까?
4. 폼과 상호작용합니다. 레이블이 읽힙니까? 오류 메시지가 읽힙니까?
5. 동적 업데이트를 탐색합니다. 변경이 안내됩니까?

**시각 감사:**
1. 색상 대비를 확인합니다 (텍스트 4.5:1, 큰 텍스트 3:1, UI 컴포넌트 3:1)
2. 200%로 확대합니다. 레이아웃이 깨지거나 겹칩니까?
3. 강제 색상 / 고대비 모드(Windows 고대비)로 테스트합니다
4. 동작 줄이기(prefers-reduced-motion)를 켭니다. 애니메이션이 꺼집니까?
5. 포커스 가시성을 테스트합니다. 포커스 링이 모든 배경에서 보입니까?

### 4단계: 위반 수정

각 발견 사항에 다음 순서로 수정을 적용하세요.

1. **근본 원인을 고칩니다**: `<div>`를 `<button>`으로 바꾸고, `<label>`을 추가하고, `alt` 텍스트를 설정합니다
2. **ARIA는 다리로 추가합니다**: 네이티브 HTML로 패턴을 표현할 수 없을 때 ARIA 속성을 추가합니다
3. **수정을 테스트합니다**: 자동화 검사와 수동 검증을 다시 실행합니다

접근성 체크리스트(`../../references/accessibility-checklist.md`)를 최소 기준으로 적용하세요.

## 흔한 합리화

| 합리화 | 현실 |
|---|---|
| "a11y는 나중에 고치자" | 수정을 미루면 컴포넌트마다 부담이 누적되고 법적 책임이 생길 수 있습니다. 출시 전에 감사하세요. |
| "자동화 도구가 전부 잡았다" | 자동화 검사는 키보드나 스크린 리더 동작을 증명할 수 없습니다. 수동 테스트는 필수입니다. |
| "스크린 리더 사용자는 극소수다" | 접근성은 요구 사항이지 사용 비율 계산이 아닙니다. 키보드 탐색, 자막, 명확한 구조는 다양한 상황의 사용자에게도 도움이 됩니다. |
| "이건 내부 도구라 a11y가 필요 없다" | 내부 도구도 같은 규정의 적용을 받습니다. 장애가 있는 직원과 계약자도 접근해야 합니다. |
| "그냥 어디서나 aria-label을 쓰면 된다" | ARIA는 다리이지 기반이 아닙니다. 시맨틱 HTML이 먼저입니다. ARIA를 남용하면 유지 보수 부담이 생기고 오히려 나빠질 수 있습니다. |
| "디자인 시스템이 접근성을 처리한다" | 디자인 시스템은 접근 가능한 기본 요소를 제공합니다. 그것을 어떻게 조합하느냐가 결과의 접근성을 결정합니다. |
| "감사가 axe-core를 통과했으니 끝났다" | axe-core 통과는 연기 테스트로만 취급하고, 이어서 스크린 리더와 키보드로 테스트하세요. Lighthouse 점수가 녹색이라고 건강 진단이 깨끗한 것은 아닙니다. |

## 레드 플래그

- 클릭할 수 있어 보이지만 키보드로 포커스할 수 없는 요소
- 상태의 유일한 표시로 쓰는 색상 (오류는 빨강, 성공은 초록)
- 눈에 보이는 대체물 없이 제거한 포커스 윤곽선
- 폼 입력의 레이블 누락
- 제목 계층이 없거나 제목 수준을 건너뜀
- 비어 있거나 레이블이 없는 버튼과 링크
- 포커스를 가두지 않거나 닫을 때 포커스를 복원하지 않는 모달
- 의미 있는 이미지에 `alt` 텍스트가 없음 (또는 장식 이미지에 `alt=""`가 없음)
- SC 2.5.8의 24x24 CSS px 크기-또는-간격 요구 사항을 충족하지 못하고 예외에도 해당하지 않는 터치 대상 (AA. 44x44는 AAA 목표, SC 2.5.5)
- 컨트롤 없이 자동 재생되는 비디오나 오디오
- 낮은 대비의 텍스트 (특히 호버, 비활성 상태, 플레이스홀더)

## 검증

접근성 워크플로우를 마친 뒤:

- [ ] 자동화 감사가 Critical이나 Serious 위반 없이 통과합니다
- [ ] 모든 상호작용 요소를 키보드로 쓸 수 있습니다 (Tab, Enter, Escape, 화살표 키)
- [ ] 제목, 랜드마크, 링크 기준의 스크린 리더 탐색을 이름이 명시된 브라우저 + 보조 기술 조합으로 검증했습니다 (또는 `manual`로 기록하고 미검증으로 표시했습니다. 검증된 것으로 보고하지 마세요)
- [ ] 포커스 순서가 시각 순서와 일치합니다
- [ ] 색상 대비가 텍스트 4.5:1 / 큰 텍스트 3:1 / UI 컴포넌트 3:1을 통과합니다
- [ ] 모든 폼 입력에 연결된 레이블이 있습니다
- [ ] 모든 이미지에 적절한 `alt` 텍스트가 있습니다
- [ ] 동적 콘텐츠 변경이 안내됩니다 (aria-live)
- [ ] 200% 확대에서 콘텐츠 손실 없이 페이지를 쓸 수 있습니다
- [ ] 터치 대상이 SC 2.5.8의 24x24 CSS px 크기-또는-간격 요구 사항이나 규범적 예외를 충족합니다 (AA). 44x44는 강화된 AAA 목표입니다 (SC 2.5.5)
