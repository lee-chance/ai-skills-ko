# 아이데이션 프레임워크 참조

이 프레임워크는 골라서 쓰세요. 아이디어에 맞는 렌즈를 고르세요. 모든 프레임워크를 기계적으로 돌리지 마세요. 목표는 체크리스트를 따르는 것이 아니라 사고를 여는 것입니다.

## SCAMPER

SCAMPER는 Substitute, Combine, Adapt, Modify, Put to other uses, Eliminate, Reverse의 머리글자입니다. 기존 아이디어에 일곱 가지 조작을 적용해 바꾸는 구조적인 방법입니다.

- **Substitute (대체):** 어떤 구성 요소, 재료, 프로세스를 바꿀 수 있을까요? 핵심 기술을 바꾼다면? 대상 사용자는? 비즈니스 모델은?
- **Combine (결합):** 다른 제품, 서비스, 아이디어와 합친다면? 보통 함께 있지 않은 두 가지가 새것을 만든다면?
- **Adapt (적응):** 이것과 비슷한 것은 무엇인가요? 다른 산업, 도메인, 시대에서 빌릴 아이디어는? 자연에 있는 평행 사례는?
- **Modify (Magnify/Minimize, 확대/축소):** 10배 크게 하면? 10배 작게 하면? 한 기능을 과장하면? 절대 최소까지 덜어내면?
- **Put to other uses (다른 용도로 쓰기):** 다른 누가 이것을 쓸 수 있나요? 다른 어떤 문제를 풀 수 있나요? 완전히 다른 맥락에서 쓰면 어떻게 되나요?
- **Eliminate (제거):** 기능을 통째로 빼면 어떻게 되나요? 설정이 전혀 없는 버전은? 단계가 절반이면 어떤 모습인가요?
- **Reverse/Rearrange (역순/재배치):** 단계를 반대 순서로 하면? 시스템이 아니라 사용자가 일을 하면 (또는 그 반대라면)? 가치 사슬을 뒤집으면?

**적합한 경우:** 기존 제품이나 기능을 개선하거나 다시 상상할 때. 그린필드 아이디어에는 덜 유용합니다.

## How Might We (HMW)

"How Might We..." 형식으로 문제를 기회로 다시 프레이밍합니다.

- 관찰이나 고통 지점에서 시작하세요
- "How might we [원하는 결과] for [구체적인 사용자] without [핵심 제약 조건]?"으로 다시 프레이밍하세요
- 같은 문제의 HMW 프레이밍을 여러 개 만드세요. 프레이밍이 달라지면 풀리는 해결책도 달라집니다

**좋은 HMW의 성질:**
- 실행할 수 있을 만큼 좁음 ("...help new users find relevant content in their first 5 minutes" / 신규 사용자가 처음 5분 안에 관련 콘텐츠를 찾도록 돕기)
- 창의적 해결을 허용할 만큼 넓음 ("...add a recommendation sidebar" / 추천 사이드바를 추가하기처럼 해결책을 지정하지 않음)
- 창의성을 강제하는 긴장이나 제약 조건이 들어 있음

**나쁜 HMW의 성질:**
- 너무 넓음: "How might we make users happy?" (사용자를 행복하게 하려면?)
- 너무 좁음: "How might we add a button to the settings page?" (설정 페이지에 버튼을 추가하려면?)
- 해결책이 박혀 있음: "How might we build a chatbot for support?" (지원용 챗봇을 만들려면?)

**적합한 경우:** 막힌 사고를 다시 프레이밍할 때. 누군가가 해결책에 닻을 내렸다면, 문제로 다시 끌어오세요.

## First Principles Thinking

아이디어를 근본적인 진실까지 분해한 다음, 거기에서 다시 쌓습니다.

1. **참으로 아는 것은 무엇인가요?** (가정된 것도, 관례도 아닌, 실제로 참인 것)
2. **무엇을 가정하고 있나요?** 당연하게 느껴지는 것까지 모든 가정을 나열하세요
3. **어느 가정에 도전할 수 있나요?** 각각에 대해 물으세요. "이것은 실제로 물리 법칙인가요, 아니면 그동안 해 온 방식인가요?"
4. **진실에서 다시 쌓으세요.** 근본적인 진실만 있다면 무엇을 만들까요?

**적합한 경우:** 점진적 사고에서 벗어날 때. 모든 아이디어가 현상 유지의 작은 개선처럼 느껴질 때.

## Jobs to Be Done (JTBD)

사용자가 말로는 원한다고 하는 것이 아니라, 실제로 해내려는 일에 집중합니다.

- **Functional job (기능적 직무):** 완료하려는 작업은 무엇인가요?
- **Emotional job (감정적 직무):** 어떤 기분을 느끼고 싶나요?
- **Social job (사회적 직무):** 어떻게 보이고 싶나요?

형식: "When I [상황], I want to [동기], so I can [기대 결과]."

**핵심 통찰:** 사람은 제품을 사지 않습니다. 어떤 일을 하라고 고용합니다. 경쟁 제품이 항상 같은 범주에 있지는 않습니다. (Netflix는 다른 스트리밍 서비스만이 아니라 수면과도 경쟁합니다.)

**적합한 경우:** 진짜 문제를 이해할 때. 옳은 것을 풀고 있는지 확실하지 않을 때.

## Constraint-Based Ideation

창의적 해결을 강제하려고 일부러 제약 조건을 겁니다.

- **시간 제약:** "이것을 만드는 데 하루밖에 없다면?"
- **기능 제약:** "기능이 하나뿐일 수 있다면?"
- **기술 제약:** "[당연한 기술]을 쓸 수 없다면?"
- **비용 제약:** "영원히 무료여야 한다면?"
- **사용자 제약:** "사용자가 컴퓨터를 한 번도 써 본 적이 없다면?"
- **규모 제약:** "사용자 10억 명에게 작동해야 한다면? 단 10명이라면?"

**적합한 경우:** 복잡함을 뚫고 나갈 때. 아이디어가 너무 커지거나 너무 모호해질 때.

## Pre-mortem

아이디어가 이미 실패했다고 상상하고, 거기서 거꾸로 올라옵니다.

1. 지금부터 12개월 뒤입니다. 프로젝트는 출시되었고 실패했습니다. 무엇이 잘못되었나요?
2. 실패의 그럴듯한 이유를 모두 나열하세요. 기술, 시장, 팀, 타이밍.
3. 각 실패 모드에 대해: 막을 수 있나요? 아이디어를 바꿔야 한다는 신호인가요?
4. 어느 실패 모드를 받아들일 의향이 있나요? 어느 것이 프로젝트를 죽이나요?

**적합한 경우:** 2단계 (Phase 2) 평가. 좋아 보이지만 아직 스트레스 테스트를 거치지 않은 아이디어를 시험할 때.

## Analogous Inspiration

다른 영역이 비슷한 문제를 어떻게 풀었는지 봅니다.

- 이 문제의 한 버전을 이미 푼 산업은 어디인가요?
- [특정 회사/제품]이 만든다면 어떤 모습일까요?
- 어떤 자연 시스템이 이렇게 작동하나요?
- 어떤 역사적 선례가 있나요?

핵심은 표면이 아니라 *구조적* 유사성을 찾는 것입니다. "Uber for X"는 표면적입니다. "낯선 사람 사이의 신뢰 문제를 푸는 양면 마켓플레이스"는 구조적입니다.

**적합한 경우:** 1단계 (Phase 1) 확장. 당연한 접근과 진짜로 다른 느낌이 나는 변형을 만들 때.
