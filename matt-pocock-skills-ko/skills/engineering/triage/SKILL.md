# Triage

프로젝트 이슈 트래커의 이슈를 트리아지 역할의 작은 상태 머신을 통해 이동합니다.

이 저장소가 외부 풀 리퀘스트를 요청 표면으로 취급하면(이슈 트래커 구성 참조), 트리아지는 그것들도 다룹니다: **PR은 첨부된 코드가 있는 이슈**이며, 같은 역할, 같은 상태, 같은 머신을 사용하고, 아래에 "PR의 경우"로 표시된 몇 가지 델타가 있습니다. 베어 `#42`를 트래커 구성에 따라 이슈 또는 PR로 해결하세요.

트리아지 중 이슈 트래커에 게시된 모든 댓글 또는 이슈는 **반드시** 이 면책 조항으로 시작해야 합니다:

```
> *This was generated by AI during triage.*
```

## 참조 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 지속 가능한 에이전트 브리프를 작성하는 방법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 지식 베이스가 작동하는 방법

## 역할

두 **카테고리** 역할:

- `bug`: 무언가가 깨짐
- `enhancement`: 새로운 기능 또는 개선

다섯 **상태** 역할:

- `needs-triage`: 유지보수자가 평가해야 함
- `needs-info`: 보고자의 추가 정보를 기다림
- `ready-for-agent`: 완전히 지정됨, AFK 에이전트 준비
- `ready-for-human`: 인간 구현 필요
- `wontfix`: 조치되지 않음

PR의 경우, 같은 상태가 첨부된 코드에 대해 읽힙니다: `ready-for-agent`는 브리프가 첨부되고 에이전트가 diff에 다음 단계를 취해야 함을 의미합니다. `ready-for-human`은 인간이 병합할 준비가 되었음을 의미합니다.

모든 트리아지된 이슈는 정확히 하나의 카테고리 역할과 하나의 상태 역할을 담아야 합니다. 상태 역할이 충돌하면, 플래그하고 다른 것을 하기 전에 유지보수자에게 물어보세요.

이것들은 정규 역할 이름입니다. 이슈 트래커에서 사용되는 실제 라벨 문자열은 다를 수 있습니다. 매핑이 여러분에게 제공되었어야 합니다. 그렇지 않으면, 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 말하세요.

상태 전환: 라벨이 없는 이슈는 일반적으로 먼저 `needs-triage`로 갑니다. 거기서 `needs-info`, `ready-for-agent`, `ready-for-human`, 또는 `wontfix`로 이동합니다. `needs-info`는 보고자가 응답하면 `needs-triage`로 돌아갑니다. 유지보수자는 언제든지 재정의할 수 있습니다. 비정상적으로 보이는 전환을 플래그하고 진행하기 전에 물어보세요.

## 호출

유지보수자가 `/triage`를 호출하고 자연어로 원하는 것을 설명합니다. 요청을 해석하고 행동하세요. 예제:

- "내 주의가 필요한 것을 보여 주세요"
- "42번을 봅시다" (이슈 또는 PR)
- "42번을 ready-for-agent로 옮기세요"
- "에이전트가 집을 준비가 된 것은 무엇인가요?"

## 주의가 필요한 것 보여주기

이슈 트래커를 쿼리하고 세 개의 버킷을 제시하세요. 가장 오래된 것 먼저:

1. **라벨 없음**: 트리아지되지 않음.
2. **`needs-triage`**: 평가 진행 중.
3. **마지막 트리아지 노트 이후 보고자 활동이 있는 `needs-info`**: 재평가 필요.

PR이 범위 내에 있으면, 이 버킷에 외부 PR을 포함하고 각 줄을 `[PR]` 또는 `[issue]`로 태그하세요. 발견은 *외부* PR만 표면화합니다(트래커 구성은 누가 외부인지 정의), 따라서 협력자의 진행 중 PR은 트리아지 작업이 아닙니다. 이 필터는 발견만입니다. 명시적으로 명명된 PR은 작성자와 관계없이 항상 트리아지됩니다.

카운트와 항목당 한 줄 요약을 보여주세요. 유지보수자가 선택하도록 하세요.

## 특정 이슈 또는 PR 트리아지

1. **컨텍스트를 수집하세요.** 전체 이슈 또는 PR(본문, 댓글, 라벨, 작성자, 날짜; PR의 경우 diff도)을 읽으세요. 해결된 질문을 다시 묻지 않도록 이전 트리아지 노트를 파싱하세요. 프로젝트의 도메인 용어집을 사용하여 코드베이스를 탐색하고, 영역의 ADR을 존중하세요. 코드베이스에 대해 두 가지 검사를 실행하세요: (a) **중복성**: 도메인 개념으로(요청의 표현뿐만 아니라) 요청된 동작의 기존 구현을 검색하고, 어디를 봤는지 보고하세요. 발견되면, 이미 구현된 `wontfix`입니다(5단계). (b) **이전 거부**: `.out-of-scope/*.md`를 읽고 이 요청과 유사한 것을 표면화하세요.

2. **추천하세요.** 유지보수자에게 추론과 함께 카테고리와 상태 추천을 말하고, 요청과 관련된 간략한 코드베이스 요약(이미 구현되었는지 포함)을 더하세요. 지시를 기다리세요.

3. **주장을 검증하세요.** 그릴링 전에, 주장이 유지되는지 확인하세요. 버그의 경우, 보고자의 단계에서 재현하세요. PR의 경우, diff가 주장하는 것을 하는지 확인하세요: 체크아웃하고, 관련 테스트나 명령을 실행하세요. 무슨 일이 일어났는지 보고하세요: 확인됨(코드 경로와 함께), 실패, 또는 불충분한 세부 사항(강한 `needs-info` 신호). 확인된 검증은 훨씬 더 강한 에이전트 브리프를 만듭니다.

4. **Grill (필요한 경우).** 요청이 구체화될 필요가 있으면, Skill 도구를 두 번, "grilling"과 "domain-modeling"으로 호출하고, 한 번에 한 라운드의 질문으로 그것을 형태로 grill하고, 도메인 용어를 다듬고, 결정이 착륙할 때 인라인으로 `GLOSSARY.md`/ADR을 업데이트하세요.

5. **결과를 적용하세요:**
   - `ready-for-agent`: 에이전트 브리프 댓글을 게시하세요([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: 에이전트 브리프와 같은 구조이지만, 위임할 수 없는 이유를 기록하세요(판단 호출, 외부 액세스, 설계 결정, 수동 테스팅).
   - `needs-info`: 트리아지 노트를 게시하세요(아래 템플릿).
   - `wontfix`의 경우, 이슈를 닫고, 댓글은 *왜*에 따라 다릅니다:
     - **이미 구현됨**: 변경이 이미 코드베이스에 존재합니다. 사는 곳을 가리키세요. `.out-of-scope/`에 작성하지 **마세요**(그 KB는 빌드된 것이 아니라 *거부된* 요청을 위한 것입니다).
     - **거부됨 (버그)**: 정중한 설명을 주고, 닫으세요.
     - **거부됨 (향상)**: `.out-of-scope/`에 작성하고, 댓글에서 링크하고, 닫으세요([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: 역할을 적용하세요. 부분 진행이 있으면 선택적 댓글.

## 빠른 상태 재정의

유지보수자가 "move #42 to ready-for-agent"라고 말하면, 그들을 신뢰하고 역할을 직접 적용하세요. 무엇을 하려는지 확인하세요(역할 변경, 댓글, 닫기), 그런 다음 행동하세요. 그릴링을 건너뛰세요. 그릴링 세션 없이 `ready-for-agent`로 이동하면, 에이전트 브리프를 작성하고 싶은지 물어보세요.

## Needs-info 템플릿

```markdown
## 분류 노트

**지금까지 확인한 것:**

- 포인트 1
- 포인트 2

**아직 여러분에게 필요한 것 (@reporter):**

- 질문 1
- 질문 2
```

그릴링 중 해결된 모든 것을 "지금까지 확인한 것" 아래에 캡처하여 작업이 손실되지 않도록 하세요. 질문은 "더 많은 정보를 제공하세요"가 아니라 구체적이고 실행 가능해야 합니다.

## 이전 세션 재개
